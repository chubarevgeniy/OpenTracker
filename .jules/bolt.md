## 2024-05-28 - Native JS Dates in High-Frequency Chart Render Loops
**Learning:** In React components that render large historical charts (like `Stats.tsx`), calling functions like `date-fns`'s `format()` and `subDays()` inside nested loops (e.g., historical TDEE tracking `calculateTDEE` which recalculates on every chart data point for up to 365 days) can cause massive CPU bottlenecks and block the main thread.
**Action:** When generating time-series data backwards iteratively over hundreds of data points, use native `new Date(endDate)` and manual `.setDate(d.getDate() - 1)` alongside manual string padding (`String(d.getMonth()+1).padStart(2,'0')`) instead of library functions. Additionally, avoid `Object.values().forEach` mapping over nested structures, preferring manual direct loop access (e.g. `m.breakfast.length`). This reduced iteration time from ~85ms down to ~6ms in benchmarking.

## 2024-05-29 - O(N) Linear Scans Over O(N log N) Object Mapping for Date Extrema
**Learning:** Using `Object.keys(map).sort()` inside hot rendering paths (like chart data generation or dashboard mounts) to find the most recent or earliest dates creates unnecessary array allocation and O(N log N) processing overhead, causing noticeable frame drops as the `dailyLogs` map grows over time.
**Action:** Always prefer direct O(N) linear scans with a `for...in` loop to identify extrema (min/max dates) in dictionary structures in this codebase, avoiding intermediate array creation and sorting entirely.
## 2024-05-18 - Replacing Object.keys().sort() and Array.reverse() for performance
**Learning:** In a performance sensitive path (`calculateTDEE` which is called during Stats rendering), `Object.keys().sort()` or `[...array].reverse()` cause memory allocations and unnecessary CPU overhead. Simple `for` loop scans are measurably faster and have fewer side effects than creating object or array copies just to traverse backwards or find values. However, make sure logic maintains exactly the same semantics. For instance, testing an optional numerical value like `weight` should be `if (obj.weight)` (like the original `.find(l => l.weight)`) rather than `if (obj.weight !== undefined)` which would wrongly include `0` or `null`.
**Action:** Default to `for` loops and variable pointers (scanning from both ends as needed) instead of spread operators, `reverse()`, and `find()` when locating specific items (like first/last weight entries) in performance-sensitive arrays.
## 2024-06-04 - React.memo Referential Equality Trap in Zustand
**Learning:** When using deeply nested state in Zustand (like `dailyLogs: Record<string, DailyLog>`) with `React.memo`, providing inline fallback defaults (e.g. `meals: { breakfast: [], ... }`) during render defeats memoization. When the requested item is absent (e.g., an empty day), the inline object creates a new reference on every single render (such as during text input keystrokes in a completely unrelated child component), causing all child components receiving that fallback to re-render.
**Action:** Always define complex fallback structures (like `DEFAULT_MEALS`) as constants *outside* the React component. This preserves referential equality across renders, allowing `React.memo` to successfully bail out of rendering child components when the parent re-renders for unrelated reasons.
## 2024-06-06 - Merging array iterations for derived state
**Learning:** Calculating multiple related derived metrics (like macros: calories, protein, carbs, fat) from a single array using separate `.reduce()` passes causes unnecessary O(N) array traversals on every render, which is exacerbated when the array size grows.
**Action:** Combine multiple array iterations into a single `for` loop pass to calculate all related derived states at once. Always wrap this single-pass calculation in a `useMemo` so that the variables are only recalculated when the underlying array reference changes, preventing expensive recalculations during unrelated local UI state updates (like typing in inputs).
